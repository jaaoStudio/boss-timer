# 登入狀態由伺服器唯一判斷

前端開頁時原本自己判斷登入狀態：先打 `/auth/session` 取得匿名身分，再打 `/auth/validate`；`valid:false` 且 localStorage 有 `user_info` 時呼叫 `/auth/refresh` 換發，再驗證一次，並依各步驟的失敗類型（401、429、網路錯誤、5xx）決定保留登入、改為匿名或清掉舊 cookie。登入狀態因此有四個來源——`user_info`、validate、refresh、WebSocket 握手時伺服器依 cookie 的判斷——每多處理一種失敗，就多一個與伺服器判斷不一致的可能。PR #58 連續三輪審查都在這段找到新問題（#59）。

我們決定**登入狀態只由伺服器判斷**：開頁只呼叫一次 `POST /auth/session`，它直接回答「你是誰」，前端照結果設定，不再自己換發或重新驗證。

- 登入有效 → `{ status: "authenticated", user }`。access token 過期、refresh token 有效時，伺服器順便換發 access token cookie。
- 有登入 cookie 但登入已失效（refresh token 無效、被撤銷，或使用者已刪除）→ 伺服器清掉舊的登入 cookie，改以匿名回應 `{ status: "anonymous", anonymous_user_id }`（沿用或發放匿名身分）。
- 撞到匿名身分發放上限時，一律回 `{ status: "anonymous", anonymous_user_id: null }`（暫時沒有身分、以 IP 限流，下次查詢再申請），**不回 429**。伺服器端的結果與 429 相同（拿不到身分），但 429 會讓前端當成判斷失敗、沿用上次的顯示：開了多個分頁時，一個分頁發現登入已失效、清掉共用的登入 cookie，其他分頁重新判斷時就變成「新訪客撞到上限」，拿到 429 而繼續顯示登入（PR #64 第 5 輪）。第一次來的訪客也不會再看到與自己操作無關的「請求太頻繁」提示。
- 有登入 cookie 就照「登入已失效」處理、清掉，不先檢查 token 能否解開：解不開的 cookie 留著沒有用，判斷規則也少一種。
- 登入者的判斷（access token 且使用者存在 → refresh token 查資料庫確認未撤銷）與 WebSocket 握手共用 `resolve_login()`，兩邊不會判斷出不同結果。
- 呼叫失敗（網路錯誤、5xx、429）不代表登入狀態改變：前端沿用目前的顯示（開頁時以顯示快取 `user_info` 恢復上次的狀態），什麼都不清除，也不自動重試，等下一次觸發再問。這個查詢不經全域錯誤處理（不跳維護 / 錯誤頁、不提示）；伺服器真的掛掉時，開頁緊接著的維護狀態請求會帶使用者到維護頁或錯誤頁。
- 額度：`/auth/session` 的個人額度依序以 access token 的使用者、該 refresh token（jti）計算，不退回 IP，同 IP 的人不會互相擋到（ADR-0007）。refresh token 只解開、不查撤銷，所以以 token 本身而不是裡面的使用者計算：重送舊的或被撤銷的 token 只用掉那個 token 的額度。代價是手上有很多舊 token 的人可以輪流使用、各拿一份額度，由 IP 天花板擋下，與匿名身分相同。

### 跨分頁同步（照 NextAuth 前端的模型）

每個瀏覽器只有一組登入 cookie，卻有好幾個分頁各自顯示登入狀態，各有一條在握手時就固定身分的 WebSocket。PR #64 前幾輪逐一補上計數器、重試迴圈、初始化去重與各種通知特例，每輪審查仍在同一區找到新問題（第 8 輪：重新判斷失敗仍重連、同一分頁同時跑好幾個判斷、被丟棄的請求觸發全域錯誤處理）。因此改用 NextAuth 前端的完整模型，讓所有分頁即時一致，以 TanStack Vue Query 實作：

- **每個分頁只有一個「我是誰」的查詢**，同時只有一個請求；任何觸發遇到進行中的請求就共用它。
- **何時查詢**：開頁；切回這個分頁（`refetchOnWindowFocus`，一律重新問）；收到其他分頁的 `LOGIN` / `LOGOUT`，或在本分頁登入、登出後。後三種代表共用的 cookie 改變過：先取消進行中的請求（它是改變前送出的），再重新查詢。取消只保證舊的結果不套用到畫面：回應標頭已經到了的話，瀏覽器仍會套用它的 Set-Cookie，伺服器端的副作用也已發生（見下方 Consequences 接受的時序）。收到通知時不採用通知裡的狀態：它可能已過時，以伺服器對當下 cookie 的判斷為準，各分頁才會一致。
- **WebSocket 何時重連**：查詢成功時，伺服器回答的身分（`user:{id}` / `anon:{id}` / 沒有身分）和 WebSocket 目前用的不同才重連。查詢失敗時不知道現在的身分：期間有人登入或登出過，就照目前的 cookie 重連，否則不重連。開頁時第一次判斷完成（成功或失敗）才連線。
- **何時通知其他分頁**：改變共用顯示快取 `user_info` 的分頁負責通知。變成沒有登入，通知 `LOGOUT`；變成另一個登入者（含從沒有變有），通知 `LOGIN`。這一條涵蓋登入、登出（先只清本分頁的畫面，取得匿名身分後才清 `user_info`、通知，其他分頁重新查詢時沿用同一個匿名身分，不會各自申請；查詢失敗也照樣清掉並通知），以及開頁或切回分頁時發現登入已失效（例如在其他裝置登入或過期，使用者沒按登出）。其他分頁收到後重新查詢，套用時快取已是新的狀態，不會再通知。同時有好幾個分頁發現登入失效（例如瀏覽器一次還原很多分頁）時，也只由第一個通知，不會互相觸發重新查詢、撞到限流。查詢失敗時以快取恢復顯示不算改變，不通知。`LOGIN` 仍帶使用者資料，只給部署切換期間仍直接套用的舊版前端使用。
- **偏好設定何時覆蓋本地**：照 CONTEXT.md 的「跨裝置同步」，帳號的偏好只在換人時載入——伺服器回答（查詢成功或登入回應）的登入者和上次套用偏好的不同時（開頁、登入、換成另一個人）；查詢失敗、改用快取時不載入。同一個人的查詢結果只更新名稱、頭像、管理員等帳號資料，保留這台裝置目前的偏好，不會蓋掉存檔中或還沒存的修改。本分頁存檔時先把存的項目寫進目前的偏好再送出（各元件也是先改本地），本地永遠是使用者最後的意思，回應先後顛倒也不會改回舊值；`user_info` 快取裡的偏好也是這台裝置目前的偏好（與各元件存在 localStorage 的收藏、版面相同），一改就寫入、不等存檔結果；只在快取仍是同一個登入者時寫入，其他分頁已登出就不寫回，也不算登入者改變、不通知（PR #64 第 12、13 輪）。登入時不等後續查詢，否則查詢失敗時本地會留著匿名時的偏好，之後存檔會蓋掉帳號的設定。

### 使用中途遇到 401（#60）

需要登入的請求（偏好存檔、回饋、管理員操作）才會遇到 401；房間裡的回報走 WebSocket，身分在握手時固定，不受 access token 到期影響。

- **保持登入有效**：登入時分頁在前景每 20 分鐘查詢一次登入狀態（照 NextAuth 的 `refetchInterval`）；伺服器在 access token（30 分鐘到期）剩不到一半效期時就順便換發（照 NextAuth 的 `updateAge`），正常使用時不會遇到 401。只在失效後才換發的話，到期到下次查詢之間仍會遇到 401（PR #70 第 2 輪），縮短間隔也無法根除。分頁在背景時不查，切回來時本來就會查；匿名沒有 access token，不定期查詢。
- **401 一律當成異常，不重送**：取消進行中的查詢（可能是 access token 到期前送出的）並重新查詢，同一時間的多個 401 共用這一次。伺服器回答登入失效（CONTEXT.md「登入失效」）、而這個分頁原本顯示為登入時，提示「登入已失效」並退回首頁，只提示、退回一次；再進房間時以匿名身分使用。其他情況（仍是登入，例如休眠剛醒計時器還沒跑、查詢失敗、原本就是匿名——已顯示匿名時不再確認）不跳頁，原本的請求照樣失敗、由呼叫端提示，使用者再操作一次即可。
- 其他分頁收到通知後改為匿名、留在原地：它們沒有正在進行的動作，通知也可能來自使用者自己按的登出。顯示從登入變成匿名時（不論原因），目前頁面需要登入（管理員頁）才回首頁。
- 401 不代表登入狀態有問題的請求（Google 登入的憑證無效）帶 `skipUnauthorizedCheck`，不走這段。
- **提示分工**：interceptor 只處理呼叫端處理不了或需要全站一致的結果——網路錯誤與 503 跳維護頁、5xx 跳錯誤頁、限流器的 429 提示「操作太頻繁」、登入失效提示並回首頁。呼叫端的失敗提示一律經 `showFailure(error, 訊息)`，全域已處理過就不再顯示，同一個錯誤不會有兩個提示；全域已跳頁時呼叫端也不再導頁（`isNavigatedGlobally`），否則會蓋掉那次跳轉。限流器以外的 429（回饋的每日提交上限）、全域沒處理的 404 等由呼叫端提示失敗，例如刪除已過期房間的紀錄會提示「刪除失敗」。

## Considered Options

- **只有看得到的分頁才同步**（收到通知時先記下，等切回分頁才查詢）：請求少，但背景分頁的 WebSocket 會一直停在舊身分，直到使用者切回去；回報記錄者與畫面在這段期間不一致。
- **所有分頁共用一個背景程式（SharedWorker）負責查詢與連線**：只有一個請求、一條連線，天生一致，但 Samsung Internet 不支援、Android Chrome 到 148 版（2026 年 5 月）才支援，手機使用者比例高；之後若改用 Socket.IO 再一併評估。
- **直接採用 NextAuth（Auth.js）**：要 React / Next.js 與 Node 伺服器，與本專案（Vue + FastAPI）不合，只沿用它前端的同步模型。
- **401 時確認登入、仍是登入就悄悄重送原本的請求**（PR #70 第 1 版）：使用者感覺不到 access token 到期，但要處理多個 401 同時發生、加入的查詢是到期前送出的、加入的查詢被取消後讀到舊狀態、每個 401 各提示一次、重送多算一次額度等時序，第一輪審查就找到一串問題。改為定期換發讓 401 在正常使用時不會發生，發生時一律當成異常。
- **偏好設定即時同步**（同一個人的每次查詢都同步其他裝置改的偏好）：PR #64 第 8 輪曾採用，但偏好存在伺服器、`user.preferences`、各元件本地三份，存檔進行中的先後順序要靠「存檔期間不套用」之類的規則補，第 9～11 輪連續找到新問題。要做對得把偏好拆成獨立的查詢加樂觀更新與回滾，這不是這個網頁的主要功能，因此改為重新開頁才同步。
- **在原本的架構上逐一補特例**（計數器判斷回應是否過時、重試迴圈、初始化與重新判斷各自去重）：PR #64 第 1～8 輪的做法，每補一處又在同一區找到新問題，改用上面的完整模型。
- **跨分頁通知直接套用狀態，初始化期間收到時沿用通知、不套用回應**：曾在 PR #64 實作，但瀏覽器仍會套用過時回應的 Set-Cookie（例如 A 開頁換發 access token 的回應晚於 B 登出才到，又把 cookie 放回去），所有分頁顯示匿名、伺服器卻認為登入；補一個時序特例又冒出下一個，改為一律重新問伺服器。
- **前端自己判斷，逐一處理失敗類型（修改前的做法）**：每種失敗都要決定保留或登出，且結果要與 WebSocket 握手（伺服器依 cookie）一致；refresh token 仍有效時畫面顯示匿名、握手卻認出登入者，或反過來。補一種情況又冒出下一種，PR #58 因此無法收斂。
- **`/auth/validate` 改成也接受 refresh token**：判斷集中到伺服器，但開頁仍要先打 `/auth/session` 再打 validate，換發與清 cookie 的副作用要放進一個「查詢」端點，還要維持「永遠回 200」的契約；不如讓本來就在開頁呼叫、會設 cookie 的 `/auth/session` 一次做完。

## Consequences

- `/auth/session` 不再只是「發匿名身分」，會換發 access token、清掉失效的登入 cookie。勿把換發或清 cookie 的判斷搬回前端。
- `/auth/validate` 只供部署切換期間的舊版前端，新前端不呼叫，日後刪除（#63）。`/auth/refresh` 新前端也不再呼叫（使用中途遇到 401 改問 `/auth/session`，見上方），只供部署切換期間的舊版前端，與 `/auth/validate` 一起刪除。
- 判斷失敗時以 `user_info` 顯示上次的狀態：這段期間畫面可能與伺服器不一致，直到下一次查詢（切回分頁、登入 / 登出或收到通知）；WebSocket 仍依 cookie 由伺服器判斷，回報記錄者不受影響。
- 每次登入 / 登出，其他每個分頁各多呼叫一次 `/auth/session`（個人額度 60/min，足夠）。
- **兩個分頁的請求同時在改共用的 cookie 時，瀏覽器照最晚到的回應設定，前端無法阻止；我們接受這類時序，只保證各分頁最後顯示的狀態與 cookie 一致**（常見的登入套件如 NextAuth 也是如此）。勿為此加跨分頁上鎖或「期間收到通知就不廣播」等特例（後者曾在 PR #64 加入，反而讓下面「失效判斷 vs 登入」時剛登入的分頁一直顯示登入）。
  - 失效判斷與登入幾乎同時發生時（A 開頁確認一個已失效的舊登入，使用者同時在 C 登入），A 的回應晚到會刪掉 C 剛拿到的登入 cookie；A 照常廣播 `LOGOUT`，所有分頁顯示未登入，使用者重新登入即可。
  - 換發與登出幾乎同時發生時（例如 A 的 `/auth/session` 正以 refresh token 換發 access token，B 同時登出），伺服器本身可能在登出之後把 access token cookie 設回去（access token 無法撤銷）：登出的分頁與其他分頁重新判斷時都會照它顯示登入，與 cookie 一致。這是伺服器端的先後順序，極少發生，最晚在該 access token 30 分鐘到期後的下一次查詢修正，我們接受。
- 初始化進行中收到通知時，取消開頁的查詢、重新問過才連線 WebSocket，不會連續握手兩次。
- 每個分頁每次切回時多呼叫一次 `/auth/session`，換得背景期間在其他裝置登出、過期等變化能在使用者看到時就修正。
- 登入時以登入回應套用帳號的偏好。瀏覽器擋掉登入 cookie、後續查詢回答匿名時，本地會留著帳號的版面與收藏（同一個瀏覽器，不會外洩）；不這樣做的話，登入後查詢失敗時，匿名時的偏好會在之後存檔時蓋掉帳號的設定。我們接受前者。
- 開頁判斷失敗、以 `user_info` 恢復顯示後，快取的偏好不算已套用：第一次查詢成功時載入帳號的偏好（相當於這次開頁的載入）。這時若剛好有存檔進行中、查詢帶回存檔前的偏好，畫面會回到舊值直到重新開頁。要同時遇到開頁判斷失敗、存檔中與查詢先後顛倒才會發生，我們接受，不為此加回「存檔期間不套用」的規則。
- 每次切回分頁都查詢，所以 cookie 存不住的瀏覽器（擋 cookie、部分 App 內建網頁）每次切回都會申請新的匿名身分，在共用 IP 的環境較快用完每個 IP 的發放上限，登入者每次切回也多一次資料庫查詢。我們接受；若成為問題，替查詢設 `staleTime`（例如 30～60 秒）即可減少。
- 登出的查詢進行中剛好收到其他分頁的通知時，登出的查詢被取消重發，登出會在取得匿名身分前就清掉 `user_info` 並通知；原本沒有匿名 cookie 時，各分頁可能各申請一個匿名身分。要同時遇到兩件事才會發生，我們接受，不為此加旗標。
- 換發與登出同時發生、登出後的查詢回答仍是登入時（上面接受的時序），會當成換人重新套用帳號偏好，這台裝置還沒存的偏好會被蓋掉。極少發生，我們接受。
- 同時送出的請求遇到 401、其中一個的回應在登入失效的確認結束後才回來時，「登入已失效」之後還會多一次那個請求的失敗提示。只在登入真的失效、又剛好有多個請求同時送出時發生，我們接受。
- 查詢失敗時不知道 WebSocket 用的身分（開頁第一次就失敗，或登入 / 登出後的查詢失敗而照 cookie 重連），下一次查詢成功時會再重連一次，即使身分其實沒變。失敗本來就少見，我們接受這一次多餘的重連，不另外記錄或向伺服器確認連線身分。
