# WebSocket 連線韌性：原生 WebSocket，照 Socket.IO（engine.io v4）的連線模型

#43（背景分頁反覆重連）的根因是後端以「90 秒沒收到前端 ping」判斷斷線，把被節流或凍結、其實仍活著的分頁踢掉。移除這個判斷後，前端又無法察覺「無聲中斷」的連線（休眠喚醒、切換網路），回報會寫進死連線而無聲遺失。我們決定沿用原生 WebSocket，但**以 Socket.IO（engine.io v4）的連線模型為唯一範本逐條照做**，不自創機制；審查發現的問題若 Socket.IO 也有，照它的處理方式，它沒處理的我們也接受，不另加特例：

- **連線時宣告參數**：伺服器接受連線後第一則訊息是 `hello`（`ping_interval` 25 秒、`ping_timeout` 20 秒），對應 engine.io 的 open 封包。
- **伺服器心跳**：每 25 秒對所有連線送 `heartbeat`。engine.io v4 把心跳從用戶端改到伺服器，正是因為背景分頁的計時器不可靠。
- **用戶端逾時**：收到 `hello` 才啟動，每次心跳重新計時，超過「間隔 + 容忍」（45 秒）沒收到就關閉、走退避重連；送出訊息前若已過期，不送、直接重連（engine.io 送出前的檢查）。不分前景背景、不探測、用戶端不送 ping。
- **送出緩衝**：每條連線一個送出佇列與寫出工作（engine.io 的 writeBuffer），所有送給用戶端的訊息都放進佇列、依序送出；廣播只放進佇列、不等送出，一條收不下的連線不會拖住呼叫端與其他連線。送出失敗，或同一則訊息從開始送出算起超過 45 秒（`ping_interval` + `ping_timeout`）還送不出去，就關閉該連線（`SEND_STALL_SECONDS`）。endpoint 處理訊息出錯時也關閉連線（engine.io 出錯即關閉傳輸；uvicorn 在 app 返回時不會關閉，前端會以為還連著）。
- **伺服器端死連線**：uvicorn 協定層 ping（對應 engine.io 伺服器等不到 pong 就關閉），設定只在 `app/Dockerfile` 的 `UVICORN_WS*`。對方不收、寫出緩衝塞滿時，協定層 ping 要先寫進同一個緩衝才開始計時，永遠不會逾時（websockets legacy 的 `keepalive_ping`）；engine.io 的 pingTimeout 是獨立計時器，這時 ping 送不到、收不到 pong 仍會關閉。我們以上面的 45 秒送不出去就關閉補上，結果相同，且只看伺服器送不送得出去、不看用戶端有沒有回應（#43）。計時從某則訊息卡住才開始，加上關閉握手，實際約在對方停止接收後 45～90 秒關閉。凍結的背景分頁瀏覽器仍會先收下，極少被關閉；活躍房間的分頁凍結數小時、緩衝塞滿時仍可能關閉，engine.io 在這種情況會更早關閉，我們接受。
- **重連**：指數退避、比例抖動、不放棄；連線卡在 CONNECTING 20 秒放棄；`offline` 事件立刻關閉進入退避，`online` 不特別處理。
- **連線一次**：只在啟動時連線，之後一律交給自動重連。
- **重要訊息帶回執**：`record_boss` 帶回執與逾時，逾時告知使用者；**不照抄 Socket.IO 的離線暫存補送**（紀錄時間以伺服器收到為準，補送會讓重生時間失準）。另以 PR 實作。

與 Socket.IO 預設值不同之處只有參數：退避上限 30 秒（Socket.IO 為 5 秒；握手限制以身分計、所有分頁共用，5 秒會讓多開分頁的使用者在停機時被 4429 擋下），抖動為 ±50% 且在上限之後套用，部署停掉舊 slot 時所有人同時斷線，才分散得開。被連線限制擋下（4429）屬暫時性失敗，照 Socket.IO 對暫時性失敗的處理走退避（#56）。

## Considered Options

- **改用 Socket.IO 套件（`python-socketio` + `socket.io-client`）**：上述機制都內建，加上 Redis adapter 還能跨容器廣播、解除 ADR-0005「部署時停掉舊 slot」的限制。但整個 WS 層與協議都要重寫、新舊前後端無法混用，以目前單機、數百使用者的規模不划算；需要水平擴展時再評估。
- **只靠前端應用層 ping + 後端逾時（修改前的做法）**：後端用「沒收到前端訊息」判斷生死，背景分頁被節流 / 凍結時會被誤踢，即 #43。
- **不送伺服器心跳，改由前端探測**：分頁可見時 45 秒沒收到訊息就送 ping、10 秒沒回應就重連，背景分頁不判斷。曾在 PR #57 實作，但這是自創的混合設計，每輪審查都找到新的邊界情況（背景分頁的網路事件、探測逾時比伺服器嚴格、送出後補探測、回滾相容），補一個特例又冒出下一個，最後改回照抄 Socket.IO。
- **廣播時每條連線設送出逾時**：曾在 PR #57 實作（5 秒），但呼叫端仍要等最慢的連線，卡住的連線每次廣播都再等一次，又衍生出逾時後要不要關閉、記錄怎麼分類等自創規則，改為照 engine.io 的送出緩衝。
- **前後端各自寫死心跳參數**：簡單，但回滾到不送心跳的舊後端時，新前端每 45 秒就會重連；兩邊的數字也要手動保持一致。改由 `hello` 宣告。

## Consequences

- **勿再加「N 秒沒收到前端訊息就關閉」的應用層逾時**（#43）；用戶端判斷斷線只看伺服器訊息，勿加只在可見分頁執行的探測等特例。
- 心跳參數只在後端（`app/websocket/manager.py`）一處，前端照 `hello` 設定；協定層 ping 的設定只在 `app/Dockerfile`，只有 uvicorn 的 `websockets` 實作會主動送 ping，因此明確指定，`websockets` 套件鎖 `<16`。
- 伺服器繼續回應舊版前端送的 `ping`；舊版前端收到 `hello` / `heartbeat` 只會在 console 記一行未知訊息。
- **後端回滾到修改前的版本時，#43 會暫時重現**：新前端收不到 `hello` 就不啟動逾時（不會每 45 秒重連），但舊後端 90 秒沒收到前端訊息就關閉，背景分頁每 90 秒重連一次，直到重新整理頁面拿到舊前端。我們接受：回滾很少發生、重新整理即恢復，即使讓新前端在背景送 ping，被凍結的分頁仍送不出去。
- 凍結的分頁恢復時，逾時可能先於積壓的心跳觸發而重連一次（Socket.IO 相同）。
- 用戶端判定斷線只關閉自己這端，伺服器要等協定層 ping 逾時（約 80 秒）才釋放該連線的名額。多開分頁的筆電從休眠喚醒、全部同時重連時可能因此撞到同時連線數上限（4429），所以 4429 必須走退避重連（#56），且要在本 ADR 的變更上線前完成。
- 連線逾時（20 秒）在連線打開時就停止，不像 engine.io 等到 open 封包：照抄的話，回滾到不送 `hello` 的舊後端時每 20 秒就會重連。`hello` 是伺服器接受連線後立刻送出，兩者之間的空窗極短，我們接受。
- 送出失敗只關閉連線、不在 manager 裡清除，清理一律由該連線的 endpoint 結束時處理（才會一併更新房間人數）。佇列沒有上限（engine.io 相同）：收不下的連線累積到關閉為止（約 45～90 秒）的心跳與房間廣播，關閉時一併丟棄。
- 回滾到舊後端時，不在房間的分頁重連後收不到任何伺服器訊息，`isReconnecting` 會一直是 true；重連提示只在房間頁顯示，進房間收到 `room_state` 就清除，我們接受。
