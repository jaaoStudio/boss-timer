# WebSocket 連線韌性：原生 WebSocket 加上業界標準做法，不改用 Socket.IO

#43（背景分頁反覆重連）的根因是後端以「90 秒沒收到前端 ping」判斷斷線，把被節流或凍結、其實仍活著的分頁踢掉。移除這個判斷後，審查又指出前端無法察覺「無聲中斷」的連線（休眠喚醒、切換網路），回報會寫進死連線而無聲遺失。我們決定沿用原生 WebSocket，補齊大型服務（Socket.IO、SignalR、Phoenix Channels、Ably）共通的做法：伺服器以協定層 ping 清除死連線；用戶端在分頁可見時，以「一段時間沒收到伺服器訊息」判斷可能斷線，先送 ping 探測、沒有回應才重連；指數退避加抖動且不放棄重試；監聽 `online` / `visibilitychange`；回報帶回執（ack）；連線狀態顯示在畫面上。

## Considered Options

- **改用 Socket.IO（`python-socketio` + `socket.io-client`）**：心跳、退避重連、回執、房間都內建，加上 Redis adapter 還能跨容器廣播、解除 ADR-0005「部署時停掉舊 slot」的限制。但整個 WS 層與協議都要重寫、新舊前後端無法混用，以目前單機、數百使用者的規模不划算；需要水平擴展時再評估。
- **只靠前端應用層 ping + 後端逾時（修改前的做法）**：後端用「沒收到前端訊息」判斷生死，背景分頁被節流 / 凍結時會被誤踢，即 #43。
- **伺服器定時對所有連線送應用層心跳**（Socket.IO 的做法），用戶端以「沒收到心跳」判斷斷線：偵測速度與只靠用戶端探測相近，卻要送給所有連線（含背景分頁）、多一個全域背景任務與一條跨前後端的時間約束（心跳間隔須小於用戶端門檻）。曾實作後在 PR #57 移除。

## Consequences

- 判斷連線生死分成兩個方向：後端靠協定層 ping（瀏覽器網路層自動回應，不需執行 JS）；前端靠「分頁可見時 45 秒沒收到伺服器訊息就送 ping 探測、10 秒沒回應就重連」，背景分頁不判斷，凍結的分頁不會誤判。
- **勿再加「N 秒沒收到前端訊息就關閉」的應用層逾時**；也勿讓前端在背景分頁定時送 ping 或判斷斷線。
- 伺服器必須持續回應前端的 `ping`，新舊版本前後端混用時前端的探測才有回應（修改前的後端本來就會回 `pong`）。
- **後端回滾到修改前的版本時，#43 會暫時重現**：舊後端 90 秒沒收到前端訊息就關閉，而新前端的背景分頁不送 ping，所有背景分頁每 90 秒重連一次，直到重新整理頁面拿到舊前端。我們接受這個代價：回滾很少發生、重新整理即恢復，而且即使讓新前端在背景照樣送 ping，被凍結的分頁仍然送不出去，只能救回一部分，卻要在平常對新後端白送流量。
- 協定層 ping 的設定只在 `app/Dockerfile`（`UVICORN_WS*`）一處；只有 uvicorn 的 `websockets` 實作會主動送 ping，因此明確指定，`websockets` 套件鎖 `<16`。
